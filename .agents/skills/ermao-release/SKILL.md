# 二毛书库发布

在本仓库根目录工作。先读取 [发布与版本](../../../docs/architecture-decisions.md#发布与版本) 和 [测试执行策略](../../../docs/testing/test-execution-policy.md)。按实际修改读取对应规范，不复制版本门禁或另建发布器。

## 授权与模式

- “发布新版本”：普通正式发布。不要因为修改很小而自行改用快速模式。
- Android 仅在用户明确要求本次包含时选择。“发布正式版”“完整更新”、代码／版本变化和上次发布选择都不授权 Android；未选择时直接按服务端范围推进，不反复追问，也不为验证流程擅自构建 Android。
- “快速发布下一个补丁版本”“快速应用更新”“code-only 发布”：快速应用更新，只有服务端应用交付。
- “设计发布流程”“新增发布 skill”“修复这个 bug”：仅完成该任务，不创建正式 tag、不上传制品、不公开 Release。
- 用户已明确授权的发布直接完成必要准备与执行，不重复索要发布授权。自动验证通过后直接发布，不另设 GitHub 人工审批。

## 共同准备

确认本次变更、原失败验证及直接受影响边界；保留用户已有改动。按发布规范更新全仓版本、双语说明和索引。双语说明各按“新增／修复／注意事项”（英文 Added／Fixed／Notes）顺序列出用户可感知的内容，条目从 1 编号；没有内容的整节省略。不要把数据库迁移直接写成必须换镜像，或为凑格式写空节。未指定快速版本号时递增补丁号；明确指定则使用用户版本并校验递增。执行 `pnpm release:validate`。

发布提交冻结后同步 main/develop，核对同一 SHA；正式 tag 是唯一稳定构建入口。构建一次，发布复用该次不可变 artifact。不得移动已公开 tag 或覆盖同版本不同内容。

默认向现有用户交付应用内在线升级；普通 full 发布也产出在线更新包。只有本次修改容器镜像自身、且在线更新包无法替换所需内容时，才要求用户更新 Docker 镜像或 fnOS 包，并在“注意事项”写明原因。应用代码、依赖和数据库迁移本身不要求换镜像。full／code-only 是发布构建模式，按现有资格选择，不把 full 自动写成手动镜像升级。客户端在线更新与发布端校验的边界见[在线更新规则](../../../docs/architecture-decisions.md#在线更新的-sha-256-校验与安装保护)：客户端只校验文件 SHA-256 并保留安装保护，不降低发布端的构建、依赖和产物校验。修改固定安装器必须用新版本完整镜像/fnOS 交付；旧 v1.2.0 需在管理界面升级一次，不能指望应用更新包修复旧安装入口。

## 普通发布

版本索引条目不设置 `serverUpdate`。依照发布 ADR 执行现有 `fnos-package` workflow 和相应验收；默认不构建 Android，不再使用历史版本白名单。

开始前给出简短范围摘要：服务端模式 full／code-only、Docker 与 fnOS 是否交付、Android 不构建（用户未选择）或明确包含。明确选择 Android 后，按 [发布选择、并行与缓存](../../../docs/architecture-decisions.md#发布选择并行与缓存) 写入本次版本对应的已接纳 `release-request.targets`，或使用无请求的手动 tag Boolean 输入；不能混用。各 job 自动继续，不重复索要授权。

服务端候选、后端完整测试、可选 Android 按真实依赖并行；只在全部本次必要结果成功后汇总和发布。已选 Android 失败／取消／异常跳过不得降级。Stable 不额外构建 Beta；Beta 只在 develop 手动明确选择时运行。后端／公共契约检查不因跳过 Android 而取消。

## 快速应用更新

详细约束见 [快速应用更新](../../../docs/architecture-decisions.md#快速应用更新code-only)。

1. 选取已公开的祖先应用版本为 `baseVersion`；首次快速更新选取对应官方基础镜像的不可变摘要，连续快速版本继承前一版本的 `runtimeImage`。核对官方镜像种子版本及协议，不使用浮动标签。`ermao-library.wiki` 与系统交付无关，完全排除其检查，不读取或验证子模块内容及指针。
2. 在本次索引条目写入 `serverUpdate: { mode: "code-only", baseVersion, runtimeImage }`。不改历史版本元数据，不给旧镜像打新版本标签。
3. 在冻结提交上运行 `node scripts/release-mode.mjs --published-base`。它与 CI 共用实际变更校验；新增 Alembic 迁移时必须执行快速迁移门禁，已有迁移不可改写，平台专属客户端源码不随本次快速包交付。资格不满足时列出具体文件/规则并停止，不改元数据绕过、不静默转普通发布。发布工作流本身不能替代原 bug 的定向验收。
4. 推送同步后的发布提交及 `v<version>` tag。观察同一正式工作流的快速分支：既有镜像内编译应用、双架构打包与完整产物校验、保存不可变 artifact；不执行下载更新、安装或浏览器运行验收。
5. 自动验证通过后直接 GHCR 发布并匿名验证全部 blob，公开双语 Release，最后发布 feed；不构建/推广镜像，不生成 FPK/APK/IPA。
6. 核对工作流、Release、feed 中的版本和两种架构摘要，确认应用版本升级而镜像/fnOS 版本不变。按现有入口同步发布说明；没有实际验证的设备或远端步骤明确列出。

## 失败与完成

- 构建/依赖身份/产物校验失败：停止发布并修正直接原因，不能跳过失败门禁。
- 发布阶段失败：仅重跑失败的 publish job，复用原 artifact ID 和摘要，不重新运行成功的构建。若仅 feed/说明同步失败，复用现有维护工作流恢复。
- 已公开版本出现 bug：发布新的补丁版本，不替换已公开制品。安装失败保留日志与备份；旧请求和失败标记不阻止容器重启，按[重启规则](../../../docs/architecture-decisions.md#更新失败后的容器重启)处理。
- 完成时报告应用版本、源码 SHA、目标选择、发布方式、真实验证及公开结果；从同一 Actions 运行记录后端、镜像构建／验收、应用包及总体耗时，区分未构建 Android、并行和缓存收益；无数据不估造分钟数。不得把本地构建通过写成“已发布”。
