# 二毛图书 App 视觉与交互设计规范

> 状态：Authoritative（固定基线）
>
> 版本：1.4
>
> 生效日期：2026-08-10
>
> 适用范围：`apps/mobile` 的 iPhone、iPad、Android 手机与 Android 平板界面

本规范是移动 App 页面设计、交互设计、组件设计和视觉验收的权威基线。Apple Human Interface Guidelines（HIG）是上游设计原则，本文件把它转换为 React Native + Expo 可执行、可测试的项目规则。页面实现不得自行发明另一套视觉语言。

### 原生优先组件决策树

每个交互控件必须按以下顺序选择第一个可行方案：

1. Expo Router 提供的原生标签、堆栈、导航栏、返回行为与路由 Sheet；
2. `@expo/ui` 在 iOS 上由 SwiftUI、Android 上由 Jetpack Compose 提供的控件；
3. React Native 平台控件，例如在通用 Expo UI 控件不满足既有行为时使用 `TextInput`；
4. 只有内容没有系统等价物时，才使用小型共享自定义组件，例如图书封面、书架层板、阅读进度、扫描遮罩和编辑式内容卡片。

功能页面只向共享原生适配器传入标签、图标名、状态与动作 ID，不直接依赖原生 Host 实现。Android 原生控件可以自然呈现 Material 3，iOS 原生控件可以自然呈现 SwiftUI；本规范禁止的是页面自行仿制 Material 卡片、FAB、导航栏、按钮和动效。

业务页面禁止直接使用 React Native `Modal`、自绘 tab role、自绘返回型标题栏和按钮型 `Pressable`。内容型点击统一通过 `ContentPressable` 提供最小触摸反馈与无障碍契约。核心动作必须有可见入口，不得只依赖手势或长按。

上游依据：

- [Apple Human Interface Guidelines](https://developer.apple.com/cn/design/human-interface-guidelines/)
- [Designing for iOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ios)
- [Layout](https://developer.apple.com/design/human-interface-guidelines/layout)
- [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- [Branding](https://developer.apple.com/design/human-interface-guidelines/branding)

HIG 更新不会自动改变已发布界面。采用新的 HIG 行为或视觉材料前，必须先评估最低系统版本、Android 等价行为、无障碍和现有页面一致性，再显式更新本规范版本。

### 设计来源与工具边界

- Mobile 设计与实现以本规范、`apps/mobile/src/shared/ui` 的运行时 token 和共享组件、现有产品界面及模拟器/真机验收结果为唯一执行依据。
- Mobile 页面、流程、组件、主题、图标、动效和状态设计不得调用 Figma，也不要求创建、读取、更新或维护任何 Figma 文件、节点、组件库或设计稿。
- 当本规范没有覆盖某项视觉或交互决策时，按 HIG、现有共享组件、Web 品牌契约、双平台原生预期和可访问性要求做出最小一致决策，并在同一变更中补充本规范或记录页面级例外。
- 用户提供的截图、图片或其他静态参考可以作为输入，但必须映射到仓库内语义 token 和共享组件；外部设计工具不得成为实现、测试或验收的前置条件。
- 视觉验收以可运行代码为准，至少检查相关 Compact/Expanded、浅色/深色、`zh-CN`/`en-US`、系统字体缩放和辅助技术状态。

## 1. 已确定的设计风格

设计风格命名为：**Apple HIG × 温暖编辑感（Warm Editorial Native）**。

一句话定义：**用 Apple 式清晰层级、克制控件和自然交互承载二毛图书温暖、安静的阅读品牌，让内容始终比界面更突出。**

风格关键词：

- 清晰：一眼看懂层级、状态和下一步；
- 安静：减少无意义装饰、边框、阴影和同时出现的操作；
- 温暖：使用项目珊瑚橙、暖白和猫咪品牌资产传递亲和感；
- 内容优先：书籍、封面、标题和阅读内容是视觉主角；
- 原生感：遵循用户已经熟悉的导航、手势、表单和系统反馈；
- 自适应：在明暗主题、字体缩放、横竖屏和手机/平板宽度下保持同一信息结构。

明确不采用：

- Material Design 的组件造型、涟漪、FAB 和高海拔卡片语言；
- 全屏渐变、霓虹、赛博、拟物木纹、厚重投影或高饱和多色竞争；
- 把每个分组都包成卡片的“卡片套卡片”布局；
- 大面积、永久性的仿 Liquid Glass 或模糊背景；
- 只有手势、没有可见控件替代的核心操作；
- 在每个标题栏、页面或空状态中重复 Logo；
- 用 emoji、文字字符或不同风格图标临时充当正式功能图标。

## 2. HIG 原则在项目中的固定解释

### 2.1 层级（Hierarchy）

- 每个页面必须有一个明确的主要用户意图；一个视觉区域最多突出一个主操作。
- 先用位置、间距、字号和字重建立层级，再考虑颜色、材料和阴影。
- 导航和控件属于内容上方的操作层，但不得遮蔽主要内容或与内容争抢注意力。
- 次要信息按需展开、进入详情或放入菜单，不在首屏平铺所有能力。

### 2.2 和谐（Harmony）

- 圆角、容器与设备边缘保持同心和连续关系；同层组件使用同一圆角语义。
- 背景可以延伸到屏幕边缘，文字和交互控件必须尊重安全区与内容边距。
- 控件尺寸、间距和动态效果要适合单手握持；高频操作优先位于中下部可达区域。
- 视觉材料必须服务于层级。透明、模糊和阴影只用于区分浮层或导航层，不用于装饰普通内容。

### 2.3 一致性（Consistency）

- 同一意图在所有页面使用同一组件、图标、名称、反馈和位置模式。
- 优先采用用户熟悉的系统行为：层级式返回、标签导航、列表、表单、菜单、弹窗和模态任务。
- iOS 与 Android 共享信息架构、品牌 token 和业务组件；只有系统拥有的行为可以按平台适配。
- Android 必须保留系统返回与 predictive back；iOS 必须保留边缘返回等预期行为。平台适配不得演变成两套产品设计。

### 2.4 清晰、内容退让与有意义的深度

- 文案直接、图标精确、可交互状态可见，避免让用户猜测。
- 品牌与界面装饰必须让位于书籍和阅读内容。
- 深度只表达真实关系：背景 → 内容 → 导航/工具 → 模态。不得用阴影制造不存在的层级。
- 动画必须解释状态变化、空间关系或操作结果；没有语义的动画应删除。

## 3. 品牌契约

### 3.1 仓库内品牌来源

- 产品名：`二毛图书`
- 品牌语：`和二毛一起，安静读书`
- Web 品牌文案来源：`apps/web/lib/brand.ts`
- App 运行时主题来源：`apps/mobile/src/shared/ui/theme.ts`
- Web 浅色主题基准来源：`apps/web/styles/theme.css`
- 品牌母版图：`apps/web/public/brand/ermao-library-app-icon-v1.png`
- 当前派生 App/PWA 图标：`apps/web/public/icons/icon-192.png`、`icon-512.png` 和 `maskable-512.png`

移动端不得在运行时导入 `apps/web` 私有文件。移动端需要品牌图片时，应从批准的母版生成平台资产并纳入自己的资源管线；不得重绘、AI 重做、改色或从低分辨率派生。未来若建立跨应用品牌包，应同时迁移上述来源并更新本节。

### 3.2 品牌颜色

颜色必须通过语义 token 使用，页面和 feature 组件禁止新增硬编码品牌色。

| 语义 | 浅色 | 深色 | 用途与来源 |
| --- | --- | --- | --- |
| `brand` | `#FF4F2A` | `#FF7A59` | Web `accent`；用于 Logo 邻近品牌元素 |
| `tint` | `#FF4F2A` | `#FF9B7F` | Web `accent`；用于图标、进度、选中轮廓、导航和输入选择色 |
| `tintText` | `#A23A22` | `#FF9B7F` | 强调色的高对比文字适配；用于链接、标签和小号强调文字 |
| `tintMuted` | `#FCE6DF` | `#4B271F` | Web `accent-soft`；用于轻选中背景和低强调信息表面 |
| `actionFill` | `#FF4F2A` | `#B9432E` | Web `accent`；用于主操作实心填充 |
| `actionPressed` | `#E94320` | `#963625` | Web `accent-hover`；深色模式使用相应按下态 |
| `onAction` | `#15171B` | `#FFF9F5` | 主操作上的文字与图标；浅色使用深色前景以维持按下态 4.5:1 对比度 |
| `background` | `#FBFAF8` | `#171310` | Web `bg`；用于页面与启动屏底色 |
| `card` | `#FFFDFA` | `#211B18` | Web `panel`；用于内容表面 |

| `text` | `#17191D` | `#FFF6F3` | Web `text`；用于主要内容 |
| `textMuted` | `#77736F` | `#C8B8AF` | Web `muted`；用于次要内容 |
| `border` | `#E6E1DB` | `#3D332E` | Web `line`；用于分隔和弱边界 |
| `borderStrong` | `#D8D1C9` | `#554B44` | Web `line-strong`；用于需要更清楚轮廓的控件 |

| `danger` | `#A53A32` | `#FF9289` | Mobile 危险、错误状态，由主题测试锁定 |
| `success` | `#3F9C59` | `#7DCB92` | Web `success`；用于成功状态 |
| `warning` | `#C67B12` | `#F0B963` | Web `warning`；用于警告状态 |

`dangerMuted`、`successMuted`、`warningMuted` 和 `overlay` 继续采用已有共享组件中已经验收的语义值；它们不得被页面私自重定义。所有上述值都由 `apps/mobile/src/shared/ui/theme.ts` 提供并由主题测试锁定，变更时必须同时更新本表、消费者和对比度测试。

1.1 变更理由：品牌基础层把“品牌识别”“文字/图标 tint”和“实心主操作”拆成不同语义。旧 `accent`、`accentMuted`、`accentPressed`、`onAccent` 同时承担品牌、导航、选择和按钮职责，导致浅色主按钮前景及深色交互状态难以独立验证，因此本版移除这些无主 alias，并迁移全部现有 Mobile 消费者。

1.2 变更理由：Web 与 Mobile 的浅色基础 palette 出现偏差，尤其是 Mobile 强调色偏暗，导致同一品牌在两个客户端呈现不一致。本版以 `apps/web/styles/theme.css` 为浅色数值基准，同步背景、表面、正文、弱文字、边界、强调、按下、焦点、成功和警告色。Mobile 继续保留语义 token 与独立深色适配，不在运行时导入 Web 私有 CSS；小号强调文字使用 `tintText`，主操作使用高对比 `onAction`，确保视觉同步不牺牲可访问性。

1.3 变更理由：Mobile 已具备完整的仓库内设计规范、语义 token、共享组件、双语测试和设备验收流程，外部设计文件不再提供不可替代的信息。本版明确取消 Figma 依赖和调用要求，将可运行代码与本规范确立为设计、实现和验收依据，避免仓库实现与外部设计状态产生双重事实来源。

影响评估：iOS 与 Android 共用同一套语义 token；Compact/Expanded 布局和中英文信息结构不变。页面、卡片、启动屏和 Android adaptive icon 背景同步到 Web 浅色底色；图标、进度、选择和主操作显示更鲜明的 Web 珊瑚橙，小号文字继续达到 4.5:1 对比度。深色主题保留原有自适应值；迁移不引入新动效、平台分叉、手势依赖或文案变化。

固定用色规则：

- 珊瑚橙只表达品牌交互和当前选中，不表示警告、错误或普通装饰文本。
- 成功、警告、危险使用独立语义色，同时提供图标或文字，不得只靠颜色传达。
- 即使 `brand`、`tint` 和 `actionFill` 当前共享 Web 强调色数值，它们也不得按名字互换；每个 token 的语义和未来演进独立。小号强调文字使用 `tintText`，主按钮统一使用 `actionFill`、`actionPressed` 与 `onAction`。
- 所有自定义颜色都必须有浅色、深色和高对比度策略。新增 token 时同步检查 Web 品牌一致性，但不因此复用 Web 私有代码。

### 3.3 Logo 与 App 图标

- 猫咪图标是品牌识别核心，保持原始比例、构图、色彩和留白。
- Logo 主要用于 App 图标、首次欢迎/连接、关于页面和确有品牌上下文的空状态。
- 常规页面标题栏、标签栏、列表标题和阅读器中不重复 Logo。
- 启动屏只负责与首屏平滑衔接，不制作广告式 Logo 闪屏。
- App 图标按平台遮罩和安全区生成；不可自行增加圆角，因为最终外形由平台处理。

## 4. 布局与响应式

### 4.1 基础网格

- 使用 4 pt 基础网格；常用间距为 4、8、12、16、20、24、32、40。
- 手机页面水平内容边距默认 20 pt；紧凑设备不得低于 16 pt。
- 平板/宽窗口使用 24–32 pt 外边距，并限制正文和表单行宽；当前通用内容最大宽度为 760 pt。
- 相关内容靠近，不相关内容通过 24–32 pt 留白、分组标题或分隔线区分。
- 页面只保留一个主要纵向滚动容器；横向滚动必须有明确内容语义和可发现提示。

### 4.2 安全区与全屏内容

- 页面背景、媒体和阅读画布可以延伸到屏幕边缘；文字、按钮、输入和导航必须避开刘海、Dynamic Island、圆角和 Home Indicator。
- 状态栏默认显示。只有阅读、媒体等沉浸场景可以隐藏，并且轻触中心或明确按钮必须能恢复控件。
- 键盘出现时，焦点输入和提交操作必须保持可见；不以固定像素猜测键盘高度。
- 同时支持横竖屏。若某个沉浸场景必须限制方向，需要产品级理由和双方向旋转一致性。

### 4.3 手机与平板

- Compact：3–5 个顶级目的地使用底部标签导航；标签包含正式图标和短文本。
- Expanded：在完整布局无法稳定容纳前不提前切换；随后使用侧栏或多栏结构，并保留与标签导航相同的目的地和选中状态。
- 平板支持窗口变化、分屏、指针和键盘。收窄时先隐藏第三级信息栏，再折叠主导航。
- 不按设备名称分支布局，以可用宽度、字体尺寸和内容能力决定布局。

## 5. 形状、表面与材料

- 固定圆角层级：10 pt 用于小型控件，14 pt 用于按钮/输入/导航项，20 pt 用于大型卡片、面板和模态内容。
- 普通内容优先使用背景、留白、列表和细分隔线。卡片只用于确实需要成组或从背景抬升的内容。
- 普通卡片最多使用 hairline 边框和极轻阴影；书封、浮层、菜单和模态可以使用更明确但柔和的阴影。
- 同一视图不叠加超过两个非模态表面层级。
- Liquid Glass 作为系统导航/浮层的渐进增强，而不是品牌风格本体。只有内容确实在其后延伸、文字仍清晰、性能稳定且存在纯色回退时才使用透明或模糊。
- 系统“降低透明度”启用时必须切换为不透明高对比表面；不得用动画模糊表达状态变化。

## 6. 字体与信息层级

- 使用平台系统字体，不引入正文品牌字体。iOS 自动使用 SF/PingFang 系列，Android 使用其系统无衬线字体。
- 采用语义字号而不是页面自定义字号：Large Title 34、Title 28、Headline 17–18、Body 17、Label 16、Caption 13 pt。
- 用户可见文字不得低于 11 pt；正文默认 17 pt。
- 所有正文、标签和图标必须随系统字体设置缩放；目标是在 200% 文字尺寸下仍能完成核心任务。
- 中文与英文分别检查换行。按钮不得通过缩小字体容纳文案，优先增加高度、允许合理换行或缩短文案。
- 数字、日期、百分比和相对时间使用活动 locale；书名、作者、书架名等用户内容保持原文。
- 只用字号、字重和间距表达层级，不依赖全大写、彩色正文或过多粗体。

## 7. 图标与图像

- 使用一套项目批准、许可允许跨平台分发的矢量图标，保持一致的轮廓、端点和视觉重量。
- 常用图标视觉尺寸为 20、22 或 24 pt，触控容器仍须至少 44 × 44 pt；项目常规控件目标为 48 × 48 pt。
- 常见操作使用用户熟悉的符号；含义不明确、危险或低频图标必须配文字或无障碍标签。
- 不在 Android 分发 Apple 专属受限资源。若 iOS 使用 SF Symbols，Android 必须提供含义和重量一致的合法替代，且行为不能分叉。
- 图片保持原始宽高比，提供足够分辨率；封面裁切只能使用约定的内容模式并保留可识别主体。
- 任何图标按钮不得用文本字符、emoji 或临时数字圆点代替正式图标。

## 8. 导航与交互

### 8.1 导航模型

- 层级探索使用 push：书库 → 作品 → 媒体版本/分卷 → 阅读器。
- 顶级目的地使用标签/侧栏，不用返回按钮在顶级目的地之间跳转。
- 独立、可取消的短任务使用 sheet/modal；破坏性确认和必须立即处理的阻断信息才使用 alert。
- 返回必须回到可预测的上一个状态，并保留合理的滚动、筛选和标签状态。
- 深链、系统返回、iOS 边缘返回和页面可见返回按钮必须得出同一个业务结果。

### 8.2 控件

- 所有点击目标至少 44 × 44 pt，常规按钮高度 48 pt；相邻目标保留足够间距以避免误触。
- 一个表单或主要区域最多一个高强调主按钮。次操作用 secondary/ghost，危险操作独立分组并明确命名。
- 全宽按钮必须在安全区和页面边距内，不贴屏幕物理边缘。
- 按下、选中、加载、禁用、错误和成功状态都必须可见并有无障碍状态。
- 禁用不能代替解释。用户需要知道为什么不能操作时，提供就近说明。

### 8.3 手势

- 常用任务使用最简单、最熟悉的单指手势。
- 滑动删除、下拉刷新、拖拽排序、双击或长按等手势必须有可见入口或菜单替代。
- 手势跟手，并允许在承诺动作前取消；不可恢复操作需要明确确认或撤销机会。
- 阅读器的轻触区、滑动翻页、键盘、工具栏、目录、进度和恢复控件属于同一导航能力，必须成组设计和验收。

## 9. 页面与组件模式

### 9.1 页面结构

推荐顺序：系统/安全区 → 导航层 → 页面标题与上下文 → 主要内容 → 就近操作 → 状态与反馈。

- 大标题用于顶级或重要页面，滚动后可以收敛，但不能让用户失去所在位置。
- 列表型内容优先用列表或网格，不为每一行添加厚重卡片。
- 与某项内容相关的操作放在该内容附近；全局操作放在导航层或明确菜单中。
- 空状态只解释发生了什么、为什么重要和一个最可能的下一步，不堆叠营销文案。

### 9.2 搜索与筛选

- 搜索对书库属于主要能力，应位于易发现的主位置，并尽量提供一个统一入口。
- 搜索框包含明确占位、清除操作、提交/实时结果规则和无结果状态。
- 筛选展示当前生效状态并提供一键清除；筛选条件变更后不得悄悄丢失用户查询。

### 9.3 表单

- 输入框有持久标签，placeholder 只提供示例或格式提示，不代替标签。
- 使用合适键盘、自动填充、大小写和提交键；错误出现在字段附近，并在提交后把焦点移到首个错误。
- 异步提交防止重复操作，允许取消时提供取消；失败不得清空用户已输入内容。
- 权限请求先说明与当前任务的关系，再触发系统权限弹窗；拒绝后提供可恢复路径。

### 9.4 加载、错误与反馈

- 页面尽快显示稳定结构；短等待避免闪烁，长等待显示与内容结构匹配的进度反馈。
- 错误说明用户能理解的结果和下一步，不显示技术路径、堆栈或服务端原文。
- 成功反馈与操作规模匹配。用户已经能从界面状态看出成功时，不再弹出冗余提示。
- 重要反馈同时使用视觉、文字，适合时辅以触觉；声音或触觉不得成为唯一信号。
- 关键错误和确认不自动消失；临时提示也必须给辅助技术足够读取时间。

## 10. 动效与触觉

- 动效目的只允许是：确认输入、解释状态变化、维持空间连续性、引导注意。
- 微交互通常为 160–240 ms，页面/面板过渡通常为 240–320 ms；手势驱动过渡必须跟手，数值可因平台和距离调整。
- 弹性克制，避免连续弹跳、视差、快速缩放、闪烁和无休止循环。
- 系统“减少动态效果”启用时，移除非必要位移、缩放、弹性和视差，改为短淡入淡出或无动画。
- 触觉用于选择变化、明确完成、警告和越界等少量关键时刻，不为每次点按都震动。
- 动画和触觉不能延迟业务结果，也不能阻挡下一步操作。

## 11. 明暗主题与可访问性

以下是发布门槛，不是增强项：

- 浅色、深色跟随系统实时变化；除阅读主题等内容级需求外，不提供重复的 App 全局明暗设置。
- 普通文字对比度至少 4.5:1，大号或符合标准的强调文字至少 3:1；目标是在自定义配色中尽量达到 7:1。
- 不只依赖颜色、位置、声音、触觉或动画传达含义。
- 触控目标至少 44 × 44 pt；字体缩放、加粗文字、提高对比度、降低透明度和减少动态效果均需验收。
- 所有交互元素提供正确的 role、label、hint、value、state 和阅读顺序；装饰内容从无障碍树隐藏。
- VoiceOver、TalkBack、键盘、Switch/Voice Control 类交互和大尺寸指针不得被自定义控件阻断。
- 焦点进入模态后留在模态内，关闭后回到触发点；错误与异步状态变化需要合理播报。
- 删除、覆盖、退出未保存任务等高风险操作使用清晰动词，并提供确认、撤销或可恢复机制。

## 12. 国际化与文案语气

- 所有用户可见文案同时完成 `zh-CN` 与 `en-US`，包括无障碍文本、原生权限说明、通知、App 元数据和非 DOM 表面。
- 语气安静、直接、尊重，不用命令式责备，不把技术错误转嫁给用户。
- 标题描述对象，按钮描述动作，错误描述结果和可执行的下一步。
- 不用用户可见文案作为程序标识；插值占位在两种语言中保持一致。
- 页面在英文长文案、中文大字体和用户内容超长时仍需可操作。

## 13. 技术栈映射

Apple HIG 是设计依据，不要求采用 SwiftUI 或 UIKit。React Native + Expo 实现必须保持以下等价语义：

- 安全区：`react-native-safe-area-context`；
- 系统明暗主题：`useColorScheme` 与语义主题 token；
- 字体缩放：React Native 文本缩放能力与语义 `AppText`；
- 导航：Expo Router / React Navigation 的层级、标签、模态和平台返回能力；
- 系统状态栏、键盘、权限、触觉、减少动态效果与无障碍：使用相应平台 API 或 Expo/React Native 适配器；
- 组件复用：基础视觉组件位于 `apps/mobile/src/shared/ui`，业务 UI 位于各 feature 的 `ui`，页面 route 只做装配；
- 禁止为追求外观而复制 Apple 私有资源、绕过系统行为或导入 Web 私有组件。

## 14. 页面设计交付模板

每个新页面在实现前必须记录：

1. 用户意图与完成标准；
2. 信息层级和唯一主操作；
3. 所属导航层级、进入方式和所有返回方式；
4. 默认、加载、空、部分数据、错误、离线、无权限和成功状态；
5. 点按、滑动、长按、键盘/指针及手势替代入口；
6. Compact、Expanded、横屏和分屏行为；
7. 浅色、深色、高对比度、减少动态效果和降低透明度行为；
8. Dynamic Type / 系统大字体、VoiceOver/TalkBack 焦点与播报；
9. `zh-CN`、`en-US` 以及超长用户内容；
10. 使用的共享组件、token 和新增设计决策。

页面若不能回答以上项目，不能进入视觉完成状态。

## 15. 验收矩阵与变更规则

最低视觉与交互验收组合：

- 手机窄宽、常规手机、平板/宽窗口；
- 竖屏、横屏、平板分屏；
- 浅色、深色；
- 默认字体、最大可支持字体、加粗文字；
- 中文、英文、超长书名/作者名；
- VoiceOver/TalkBack；
- 减少动态效果、降低透明度、提高对比度；
- 触摸、系统返回；平板页面另验收键盘与指针。

规范变更必须：

1. 说明对应的用户问题或 HIG 上游变化；
2. 评估 iOS、Android、手机、平板、双语和无障碍影响；
3. 更新本文件版本和相关 token/共享组件；
4. 迁移所有受影响页面，不能长期保留两套模式；
5. 通过 Mobile lint、typecheck、test、i18n 和适用的设备视觉验收。

页面级例外必须记录原因、影响范围、替代无障碍行为和删除条件。仅以“更好看”“参考图如此”或“实现方便”为理由，不构成例外。
