# Mobile App 离线技术方案对比

- 状态：v1.0.0 发布后再评估；不是当前实现要求，也不替代 ADR 0015
- 日期：2026-08-15
- 范围：手机客户端登录恢复、GET 数据缓存、已下载图书与 Reader 本地数据

## 1. 共同目标

> v1.0.0 明确不实现本文方案 A 或方案 B。当前发布契约见 [`ADR 0015`](adr/0015-mobile-v1-verified-session-without-offline-mode.md)：正常 Shell 的已验证会话恢复、网络页面局部失败、无独立离线模式、无 GET 持久回退。

- 用户至少成功登录一次后，本地保留服务器、用户和会话信息。
- 断网、超时、DNS、TLS 或服务器 `5xx` 不清除本地登录态。
- 只有服务端明确返回鉴权失效、会话过期或账户停用，才清除当前登录态和用户信息。
- 无论采用哪一种方案，网络和服务端设置异常都不能阻断已下载图书的阅读。
- 用户密码不作为离线能力的一部分持久化；持久 Cookie 继续由 Android Keystore 和 iOS Keychain 保护。

## 2. 方案 A：版本化 GET 缓存，在线界面自然降级

### 2.1 缓存规则

客户端维护独立的 `CACHE_SCHEMA_VERSION`，不直接使用 App 的版本号。缓存保存为：

```json
{
  "schemaVersion": 1,
  "savedAtEpochMillis": 0,
  "payload": {}
}
```

读取规则：

1. 本地缓存存在、可解析且 `schemaVersion` 与当前客户端一致时，立即展示缓存内容。
2. 在线时可以在后台刷新；刷新成功后原子覆盖缓存。
3. 刷新失败时继续展示已有缓存，不先清空页面。
4. 缓存版本不一致或无法解析时，直接丢弃该缓存并请求服务器。
5. 丢弃缓存后如果设备离线，页面显示正常空状态或局部不可用状态，不阻断 App、Download Center 或 Reader。
6. 私有缓存继续按服务器和用户隔离，避免跨服务器或跨账号读取。

只有缓存数据结构发生不兼容变化时才提升 `CACHE_SCHEMA_VERSION`。普通 UI 修改、补丁升级或不影响缓存结构的 API 修改不需要清空缓存。

### 2.2 服务端设置

- Mobile 不支持服务端设置写入，不调用相应写接口。
- 设置 GET 有兼容缓存时展示缓存。
- 没有兼容缓存且请求失败时，仅让对应数据为空或暂不可用。
- 不显示全屏错误，不跳转登录，不影响读书主流程。

### 2.3 Reader 本地数据

- 阅读进度、书签和阅读器偏好必须先写本地。
- 阅读器偏好可以完全保留在设备，不要求服务端同步。
- 阅读进度发生变化且当时在线时，尽力把当前完整进度发送给服务器。
- 发送失败不排队、不重试、不阻断阅读；用户以后在线并再次产生进度时，再发送当时的最新完整进度。
- 因此，用户离线阅读后如果不再产生新的在线阅读事件，该段本地进度不会自动上传；卸载 App 或更换设备可能丢失尚未发送的进度。这是方案 A 接受的产品限制。

### 2.4 启动规则

- 有本地会话记录时直接进入正常 App Shell，再后台验证服务器会话。
- 没有本地会话记录时进入首次登录。
- 服务端明确返回 `401`、会话过期或账户停用时进入重新登录。
- 其他网络和服务器错误不改变本地登录状态。
- 不使用基于本地时间的离线授权有效期。

## 3. 方案 B：独立离线模式

### 3.1 产品边界

- 在线模式保持现有完整 App，包括首页、书库、详情、设置和服务端能力。
- 离线模式只能由用户显式进入；网络不可用、请求超时或服务器错误不得自动切换模式。
- 离线模式只读取本地 completed 下载 manifest，并展示已下载图书。
- 离线模式只提供 Download Center、Reader 和必要的返回/退出操作。
- 不展示首页缓存、书库缓存、服务端设置、管理功能或其他在线页面。
- Reader 仍可写本地进度、书签和偏好；同步规则可以继续采用方案 A 的尽力发送策略。

### 3.2 模式切换规则

模式、会话和网络状态必须相互独立：

```text
AppExperienceMode = OnlineShell | OfflineLibrary
SessionState      = LocalSession | ReauthenticationRequired
Connectivity      = Unknown | Available | Unavailable
```

- `AppExperienceMode` 只能由用户操作改变，不能由 `Connectivity` 改变。
- 用户在在线模式进入地铁、地下室或经历短暂网络波动时，继续停留在原页面和原导航栈。
- 在线页面的请求失败只影响当前请求；不得打开离线 Shell、重置导航或反复显示模式切换提示。
- 用户正在阅读已下载图书时，网络变化不得中断 Reader，也不得改变 Reader 所属模式。
- 在线 Shell 内的 Download Center 仍可直接读取本地下载清单；用户不必为了继续当前阅读而切换模式。
- 在线模式可以在固定入口提供“进入离线模式”，例如 Download Center 或“我的”页面；网络失败页面可以提供同一个轻量操作，但不得弹出强制确认或自动执行。
- 用户显式进入离线模式后，保存该选择；App 冷启动继续进入离线 Shell，直到用户显式退出、主动登出或收到明确鉴权失效结果。
- 网络恢复不自动退出离线模式。可以显示稳定、非阻断的“网络已恢复，退出离线模式”操作，由用户决定是否返回在线 Shell。
- 用户显式退出离线模式后立即返回在线 Shell，再在后台验证会话；暂时仍无网络时也不把用户强制送回离线模式。
- 服务端明确返回鉴权失效、会话过期或账户停用时，鉴权状态优先于模式状态，进入重新登录并清除已保存的离线模式选择。

### 3.3 隔离要求

- 在线 Shell 与离线 Shell 使用不同的根导航和可访问路由。
- 离线 Shell 不实例化依赖服务端数据的页面或 ViewModel。
- 离线图书的事实来源只能是 completed 下载 manifest 和实际存在的本地文件，不能把 GET 元数据缓存当作已下载图书。
- 离线模式不主动调用业务 API；退出离线模式后再恢复在线请求和会话验证。
- 两个 Shell 共享同一套下载 manifest、本地图书存储、Reader 引擎和本地 Reader 数据，禁止复制两套下载或阅读实现。

## 4. 对比

| 维度 | 方案 A：版本化 GET 缓存 | 方案 B：独立离线模式 |
|---|---|---|
| 初始实现量 | 中等，需要为多个 GET 页面统一接入缓存 | 较小，只需稳定的下载清单、Reader 和独立 Shell |
| 状态与导航 | 一套 Shell，但每个页面要正确处理缓存、空状态和刷新失败 | 两套根模式；模式只由用户切换，不随网络波动变化 |
| 数据一致性 | 需要维护每种缓存的版本、解析和淘汰 | 只维护下载 manifest 与本地文件，一致性更简单 |
| 后续 API 变化 | 可能需要调整对应缓存结构与版本 | 大部分在线 API 变化不影响离线模式 |
| 用户离线体验 | 更完整，可浏览最近缓存的首页、书库和详情 | 更受限，只能管理和阅读已下载图书 |
| 页面开发约束 | 所有 GET 页面都必须遵守缓存优先和失败保留规则 | 在线页面基本不需要离线适配 |
| 测试范围 | 每个缓存页面都要覆盖在线、离线、旧版本和损坏缓存 | 重点测试模式切换、下载清单和 Reader |
| 长期清晰度 | 产品体验自然，但容易出现页面间缓存策略不一致 | 产品边界最清楚，较难误把在线数据当作离线可用 |

## 5. 初步结论

如果优先级是实现最简单、职责最清晰、以后在线 API 变化尽量不影响离线能力，优先选择方案 B。方案 B 的模式切换必须是显式用户意图，不能把网络状态当作导航状态机的触发器。

如果优先级是断网后仍保留与在线模式相近的浏览体验，选择方案 A，但必须接受每个 GET 页面都要维护版本化缓存和离线空状态。

两种方案不需要同时完整实现。若产品尚未决定，可以先交付方案 B；以后确有需求时，再为少数高价值页面逐步增加方案 A 的版本化缓存。增加缓存只扩展这些页面，不改变 Download Center 和 Reader 作为离线阅读事实来源的边界。
