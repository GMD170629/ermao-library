# 启动数据迁移性能报告

日期：2026-08-11。测试环境：Apple M4、16 GiB、APFS、Python 3.11.15、
SQLite 3.50.4、SQLAlchemy 2.0.50。以下时间是本机实测或注明的线性外推，
机械盘、NAS 和低功耗设备需要保留额外余量。

## 启动约束

容器先同步执行 `python -m app.bootstrap.startup_data_migrations`，成功后才创建
Uvicorn 进程。Schema、分类映射和漫画页索引任一失败都会让命令非零退出，API
不会启动。直接启动 Uvicorn 或独立 Worker 时，lifespan/worker 入口仍会再次执行
同一幂等检查，防止绕过容器入口。

标准输出包含以下稳定记录：

- `startup_data_migrations outcome=started|success|failed`
- `library_facet_index_data_migration outcome=started|progress|success|failed`
- `comic_page_index_data_migration outcome=started|progress|success|failed`

长迁移约每 5 秒输出一次 progress，避免 5 万册场景按每个小批次打印上万行；
success/failed 始终包含最终批次、处理总量和总耗时。

## 分类映射迁移

真实 SQLite 数据包含唯一作者、每本 3–5 个标签和共享系列，平均约 6 条分类
关系。每组使用独立数据库运行两次，表中使用中位数。

| 每批作品 | 5000 本耗时 | 吞吐 | SQL | 写事务均值 | p95 | 最大值 | RSS 增量 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 25 | 5.420s | 922 本/s | 1601 | 21.8ms | 30.0ms | 55.8ms | 12.0 MiB |
| 50 | 5.055s | 989 本/s | 1201 | 42.7ms | 51.8ms | 55.1ms | 13.6 MiB |
| 100 | 4.775s | 1047 本/s | 1051 | 82.1ms | 91.7ms | 93.5ms | 15.6 MiB |
| 200 | 4.670s | 1071 本/s | 901 | 163.7ms | 172.5ms | 220.8ms | 21.1 MiB |

生产值采用 **50 本/批**。与 200 相比仅慢 7.6%，但连续写事务约缩短 74%，
内存也更低；继续放大批量的边际收益很小。按 5000 本结果线性外推，5 万本约
50.55 秒、1000 批、12001 条 SQL，约新增 94.3 MiB 索引数据。迁移后的关系计数
和数据库大小在四种批量下完全一致。

分类数据只来自数据库投影，不读取图书文件。作者拆分、标签 JSON 解析、规范化、
去重和 SQL expression 构造均在第一条 DML 前完成；写阶段使用集合 CAS、分类
UPSERT、映射查询、关系删除/插入和版本更新，并保持作品 `updatedAt` 不变。

## 漫画页索引迁移

待处理文件由 `(kind, pageIndexVersion, id)` 复合索引筛选。25 万条非漫画文件的
第一次查询为 60.84ms，warm median 0.56ms，只有 1 条 SELECT、0 DML；它们不会
进入 Python，也不会打开文件。已经完成当前索引版本的漫画同样不会读取文件。

漫画迁移只读取 ZIP/RAR 目录，不解压图片内容；仅在存在不超过 1 MiB 的
`ComicInfo.xml` 时读取该 XML。线程数 1/2/4/8 的 1000 册 warm-cache 解析分别为
1.593/1.654/1.714/1.726 秒，因此默认保持顺序读取，避免机械盘随机寻道和线程
调度开销。

生产值采用 **最多 25 册、最多 750 页/批**。短章节包可一次处理 25 册；180 页
单行本通常每批 4 册。把页预算提高到 1500 只快约 4%，却把基线写事务
median/p95 从约 72/122ms 拉到 143/199ms，因此不采用。

页候选从 14 个绑定参数降至 8 个，固定时间戳不再逐页绑定；已知 `pageCount` 会在
打开下一册前进行预算判断，避免重复读取。优化后的真实结果：

| 数据集 | 总耗时 | SQL / DML | 写事务 median / p95 | 解析次数 |
| --- | ---: | ---: | ---: | ---: |
| 1000 册 × 180 页，缺历史 pageCount | 17.458s | 2752 / 2500 | 52.69 / 105.12ms | 1249 |
| 1000 册 × 180 页，有历史 pageCount | 17.224s | 2752 / 2500 | 53.09 / 106.72ms | 1000 |

相对优化前 28.860 秒，耗时下降 39.5%，SQL 下降 31.2%，DML 下降 33.3%。极端
5 万册 × 180 页等于 900 万页，按本机结果约 **14.4–14.6 分钟**，页索引数据库
约 4.7 GiB。若是 5 万册 × 30 页，基线外推约 3.66 分钟。实际估时必须同时给出
待迁移漫画数量和平均页数，不能只按书库总作品数计算。

完整性检查覆盖 18 万页：页 ID 全部唯一、每卷页序 1–180、文件版本全部更新、
孤儿为 0、页与文件的卷册关系错配为 0。完成后幂等重跑只有 1 条 SELECT、0 DML。
新导入漫画在导入事务中直接集合写入页索引并设置当前版本，不会进入历史迁移。
API pages 与 OPDS 请求只使用持久化索引，不再包含“缺索引时扫描压缩包”的请求期
兼容分支；索引若被运行期外部操作破坏，接口返回空页/404，而不是隐藏补算。

## 结论

- 分类映射：50 本/批；5 万本本机约 51 秒。
- 漫画页索引：25 册且 750 页/批；总书库规模不产生文件读取，只有待迁移漫画会
  打开压缩包；极端 5 万册 × 180 页本机约 14.5 分钟。
- 两项迁移都在 API 启动前完成，批次提交后可从版本检查点续跑；失败保持待迁移
  状态并阻止 API 启动。
