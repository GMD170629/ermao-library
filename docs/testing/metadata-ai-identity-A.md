## 任务 B：真实网站条目对应（2026-09-27）

### 实际入口与行为

- 手动：`POST /api/books/{bookId}/source-nodes/{sourceNodeId}/metadata/search` → 原 SourceNode adapter → 已启用网站查询 → `match_metadata_candidates` → 原弹窗 → `POST /api/books/{bookId}/metadata/apply` → 详情 GET。原权限检查和保存接口保留。
- 自动：`process_metadata_lookup_task` 先遍历任务中的网站来源，收集成功候选，再调用相同的 `match_metadata_candidates`；不再让顺序靠前的 `ai-identity` 提前完成任务。一个网站失败会记录原始诊断并继续其他网站。之后保留原字段保护、本地优先、任务取消、元数据并发修改检查和写回入口。
- 模型仍使用 A 的 Source 配置及唯一 `chat_completion` 客户端。新增 match 用途严格返回 `title`、`author`、`primaryCandidateId`、`relatedCandidateIds`、`needsReview`、`reason`。只发送当前身份、本地有限线索，以及最多 20 个真实候选的原始标题作者和每条至多 1200 字符简介。每个来源最多保留 10 条，现有网站每次只查询一轮，没有额外修正查询。
- 候选键为 `来源:条目ID`，模型返回的主条目和关联条目必须存在于本次候选中。结构错误、虚构键、跨来源错键或无主条目却提供关联条目均不应用。模型不能返回简介等生成字段。
- 直接比较成功且身份无待复核项时继续走原选择器；无法直接对应时将原候选交给 AI，确认后直接采用其条目，不再用精确选择器否决。B 的最终身份和最终复核状态进入应用；空的“无对应”结果不会把 A 原有的不确定状态变成确定。
- 原候选完整保留；独立的 `selectedMetadata` 表达确认后的标准身份和可应用字段。主条目的已有值保持；关联条目仅补缺失的简介、标签、封面，不拼装 ISBN、出版社、出版日期或语言。无对应时仍提供 A 身份候选，不生成简介或标签。
- `manualQuery` 保持本次关键词；匹配可分析本次候选、修正最终身份，但响应 query 和输入框不会回到上一轮。弹窗沿用原候选列表和简短原因，允许换选条目，保存后重新读取详情。
